# 리팩토링 착수 (Start Refactoring)

## 목적

동작을 보존하면서 코드 구조를 개선한다. 리팩토링 전 `docs/refactoring/`에 계획 문서를 작성하고, 합의 후 같은 문서를 기준으로 실행한다.

핵심 원칙:

- **동작 보존** — API·에러·DB 부작용 유지
- **테스트 우선** — characterization / 회귀 테스트로 현재 동작 고정
- **책임 분리** — 레이어·정책·중복 로직 정리

- **문서 단계 (Phase A)**: 범위·동작 보존 기준·설계·테스트·롤백 정리 (코드 변경 금지)
- **실행 단계 (Phase B)**: 계획 문서 + `AGENTS.md` 기준으로 작은 단위 변경·검증

## 필요한 입력

- 대상 모듈, 파일, 또는 동작
- `AGENTS.md`
- 기존 코드베이스·테스트

## Phase A — 리팩토링 문서 작성

1. 문서 경로를 정한다. 기본: `docs/refactoring/{target-name}.refactoring.md`
2. `AGENTS.md`를 읽고 레이어·아키텍처 규칙을 확인한다.
3. `templates/refactoring-template.md`를 복사해 문서를 생성한다.
4. **In-scope / Out-of-scope**를 3~7줄로 명시한다. 기능 변경은 Out-of-scope로 분리한다.
5. **동작 보존 기준**과 **사전 고정 테스트**를 문서에 적는다.
6. 이 단계에서는 코드를 변경하지 않는다.

## Phase B — 실행

리팩토링 문서가 합의된 뒤, 사용자가 실행을 요청하면 진행한다.

1. 리팩토링 문서와 `AGENTS.md`를 읽는다.
2. **동작 고정** — characterization test 또는 기존 테스트로 현재 동작을 먼저 고정한다.
3. **설계 정리** — 불명확한 분기보다 명시적 컨텍스트·정책 객체를 우선한다. service 본문의 레이어·정책 분기를 분리하고, 중복은 정책 모듈·적절한 레이어로 이동한다.
4. **작은 단위 적용** — 한 번에 크게 바꾸지 않는다. 단계마다 pytest·lint·핵심 시나리오를 확인한다.
5. **미사용 코드 제거** — 죽은 분기, 미사용 파라미터, 중복 alias를 제거한다. 제거 전 `rg` 등으로 참조를 확인한다.
6. 구조 이동으로 레시피 skill이 필요하면 문서 표를 보고 해당 `SKILL.md` workflow를 따른다.
7. 문서의 **변경 로그·실행 메모**를 갱신한다.
8. **검증 및 보고** — 변경 파일 목록, 동작 보존 근거(테스트/시나리오), 잔여 리스크를 남긴다.
9. `review-code` skill로 마무리 검토를 권장한다.

## 가드레일

- API 응답 스키마를 변경하지 않는다.
- 에러 형식을 변경하지 않는다.
- 계획되지 않은 한 DB 문서 구조를 변경하지 않는다.
- 불필요한 추상화를 도입하지 않는다.
- 기능 변경을 리팩토링 범위에 섞지 않는다.
- 아키텍처 원칙은 `AGENTS.md`와 `.cursor/rules/`를 따른다.

## 체크리스트

- [ ] 동작 보존 기준이 문서에 명시되었는가
- [ ] 기능 변경이 리팩토링 범위에 섞이지 않았는가
- [ ] 책임·정책 분리가 적용되었는가
- [ ] 미사용 코드 제거 전 참조 검색을 했는가
- [ ] 테스트 또는 동등한 검증 근거가 있는가
- [ ] 문서(변경 로그)가 동기화되었는가

## 작성 원칙

- 리팩토링 문서는 **실행 계획**이다. 구현 후 회고처럼 쓰지 않는다.
- Goal, Non-Goals, Done Criteria를 반드시 포함한다.
- 불명확한 항목은 Open Questions로 남긴다.

## 넣지 말아야 할 것

- `AGENTS.md`와 중복되는 장문의 아키텍처 설명
- 계획과 무관한 기능 추가
- 실행 전 확정할 수 없는 결과 보고

## 자산
